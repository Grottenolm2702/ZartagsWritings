\section{Architektur}

\subsection{Komponentenstruktur}

Die Anwendung folgt einer klassischen \textbf{3-Schichten-Struktur}:
\textbf{Frontend (Präsentation)}, \textbf{Backend (API + Fachlogik)} und
\textbf{Persistenz (SQLite über Prisma)}.
Die Schichten sind klar getrennt und kommunizieren ausschließlich über
HTTP-Requests auf \texttt{/api/*}.

\paragraph{Frontend-Schicht}
Das Frontend ist als Single-Page-Anwendung mit React umgesetzt.
Die Routen in \texttt{frontend/src/App.tsx} bilden die fachlichen Bereiche ab:
Authentifizierung (\texttt{/login}, \texttt{/register}), Campaign-Übersicht
(\texttt{/campaigns/:slug}) sowie Entity-Ansichten und Bearbeitung.

Eine zentrale Rolle übernimmt der \texttt{JWTAuthContext}:
Er hält den globalen Authentifizierungszustand (\texttt{user},
\texttt{isLoggedIn}, \texttt{loading}, \texttt{error}),
führt Login/Logout aus und lädt den aktuellen Benutzer über \texttt{/api/user}.
Dadurch bleibt Auth-Logik aus den Seitenkomponenten ausgelagert und
wiederverwendbar.

Für API-Aufrufe wird ein gemeinsamer Fetch-Wrapper
(\texttt{frontend/src/lib/api.ts}) genutzt. Dieser setzt standardmäßig
\texttt{credentials: include}, damit das JWT-Cookie bei geschützten Requests
mitgesendet wird.

\paragraph{Backend-Schicht}
Das Backend ist modular in Routenpakete aufgeteilt, die in
\texttt{backend/src/server/app.ts} registriert werden:
\texttt{authRoutes}, \texttt{userRoutes}, \texttt{campaignRoutes},
\texttt{entityRoutes}, \texttt{memberRoutes}, \texttt{healthRoutes}.

Die Route-Module kapseln jeweils eine fachliche Domäne:
\begin{itemize}
  \item \textbf{Auth:} Registrierung, Login, Logout,
  \item \textbf{User:} aktuelles Profil lesen/löschen,
  \item \textbf{Campaigns:} anlegen, beitreten, laden, Join-Code regenerieren,
  \item \textbf{Entities:} Templates, Listen, Details und CRUD je Entity-Typ,
  \item \textbf{Members:} Rollen- und Anzeigenamenverwaltung innerhalb einer Campaign.
\end{itemize}

In \texttt{backend/src/server/entities.ts} liegt zentrale Domain-Logik, die von
mehreren Routen wiederverwendet wird, z.\,B.:
\texttt{loadCampaignForUser}, \texttt{serializeEntity},
\texttt{canEditCampaign}, \texttt{canManageCampaign}.
So wird verhindert, dass Autorisierungs- und Transformationslogik in mehreren
Dateien dupliziert wird.

\paragraph{Persistenz-Schicht}
Der Datenzugriff erfolgt ausschließlich über Prisma.
Die Prisma-Client-Instanz wird zentral in \texttt{config.ts} erzeugt und über
den Better-SQLite3-Adapter mit \texttt{DATABASE\_URL} verbunden.
Das reduziert Kopplung, da Routen keine eigene DB-Verbindung aufbauen.

\subsection{API-Design}

Die API ist als \textbf{REST-orientierte JSON-API} unter \texttt{/api} umgesetzt.
Für geschützte Endpunkte wird die Middleware \texttt{authenticateToken}
verwendet, die den JWT aus dem HttpOnly-Cookie validiert und den User-Kontext
an den Request hängt.

\paragraph{Konventionen}
\begin{itemize}
  \item Ressourcenorientierte Pfade, z.\,B. \texttt{/api/campaigns/:slug}.
  \item HTTP-Methoden gemäß Operation (\texttt{GET}, \texttt{POST},
  \texttt{PUT}, \texttt{PATCH}, \texttt{DELETE}).
  \item Fehlerantworten mit passendem Statuscode und JSON-Fehlermeldung
  (\texttt{\{ error: ... \}}).
  \item Rollenprüfung serverseitig vor schreibenden Aktionen.
\end{itemize}

\paragraph{Autorisierungslogik}
Die Autorisierung ist zweistufig aufgebaut:
\begin{enumerate}
  \item \textbf{Authentifizierung} über JWT-Cookie
  (\texttt{authenticateToken}).
  \item \textbf{Fachliche Berechtigungen} über Rollenprüfungen:
  \texttt{canEditCampaign} erlaubt Owner, DM und Editor;
  \texttt{canManageCampaign} erlaubt Owner und DM.
\end{enumerate}

Damit werden unzulässige Änderungen serverseitig abgefangen, auch wenn ein
Client manipulierte Requests sendet.

\subsection{Datenbankschema}

Das Datenmodell ist auf zwei Kernanforderungen ausgelegt:
\textbf{(1) Mitglieder- und Rollenverwaltung pro Campaign} und
\textbf{(2) flexible Inhaltsstruktur für unterschiedliche Entity-Typen}.

\paragraph{Kernentitäten}
\begin{itemize}
  \item \texttt{User}: registrierte Benutzer mit Login-Daten.
  \item \texttt{Campaign}: Kampagne mit Owner, Metadaten und Join-Code.
  \item \texttt{CampaignMember}: Zuordnung User $\leftrightarrow$ Campaign inkl. Rolle.
  \item \texttt{Entity}: fachliches Objekt (PC, NPC, MAGIC\_ITEM, LOCATION).
  \item \texttt{EntityField}: strukturierte Header-Felder einer Entity.
  \item \texttt{ContentBlock}: Inhaltskarten pro Entity (Text, Liste, Attribute, Bild).
  \item \texttt{ContentListItem} und \texttt{ContentAttribute}: Unterelemente für
  Listen und Attribute.
\end{itemize}

\paragraph{Relationen und Constraints}
\begin{itemize}
  \item Ein User kann in vielen Campaigns Mitglied sein; eine Campaign hat viele
  Mitglieder (\texttt{CampaignMember} als Join-Tabelle).
  \item Eine Campaign hat viele Entities; eine Entity gehört genau zu einer Campaign.
  \item Eindeutigkeit wird über fachliche Schlüssel gesichert, u.\,a.
  \texttt{Campaign.slug}, \texttt{Campaign.joinCode},
  \texttt{User.email} sowie \texttt{(campaignId, type, slug)} für Entities.
  \item Cascading-Deletes entfernen abhängige Daten konsistent
  (z.\,B. Entity $\rightarrow$ Fields/Blocks).
\end{itemize}

Das Schema kombiniert damit klare Normalisierung für Beziehungen
(\texttt{User}, \texttt{Campaign}, \texttt{CampaignMember}) mit einer flexiblen
Content-Struktur für heterogene Kampagneninhalte.
